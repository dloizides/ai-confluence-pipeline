Does the pipeline actually pull REST → update the common components?

Yes — and here's exactly which step hits REST (this is the part people get wrong):

  • figma:generate does NOT hit REST — it reads the already-extracted figma-extract.json + the correction layer. To pull a fresh value from Figma you must run figma:extract first (or figma:sync, which does extract → all generators in order).
  • A second, independent REST path builds the conformance "ruler": figma:generate:button-conformance hits /v1/files/:key/nodes directly + joins the offline token export (figma-tokens.json) for per-mode colours. (/v1/variables/local is 403; the Dev-Mode MCP is rate-limited — hence the manual token export.)

Honest scope (verified):

  • ✅ Button family (page-button, btn-action, btn-grid-*, grid-button) is fully REST-driven end-to-end and conformant in light + dark.
  • ⚠️ Controls (radio, checkbox, chevron): the conformance dataset reads their geometry from REST, but their live values come from hand-authored figma-corrections/*.json, not auto-derived per-property from REST. The pipeline can carry REST → components (proven for buttons); for controls the correction layer is the manual bridge.

E2E test walkthrough — change → regenerate → verify → revert

A concrete, copy-pasteable loop. The fastest path edits a correction value (no Figma round-trip); the fuller path edits a real Figma value/variable and re-extracts.

1. Change a value

Pick one:

  • Fastest (correction path): edit a value in scripts/figma/data/figma-corrections/*.json — e.g. figma-corrections/toggle.json → set the active-track colour to something obvious like "255 0 0".
  • Real Figma path: change the style/variable in the Figma file itself (e.g. a component fill, or a Design-Token variable like base/accent).

3. Eyeball the changed value in the portal — light AND dark

  • Open the component page, e.g. http://localhost:4448/components/toggle/native.
  • Place an X / eyeball the changed value in light, then toggle the mode switch (top-right) and eyeball it again in dark.

4. Refresh

  • Do a normal browser reload. The theme CSS variables are injected on load, so a normal reload re-injects the freshly-generated values. The client persists only mode now, so it never shadows code — no hard refresh needed.
  • ⚠️ An already-open tab keeps the OLD injected vars until you reload. A change to vite.config.ts needs a full dev-server restart (not HMR).

5. Change it back

  • Revert the Figma / correction edit (git-restore the figma-corrections/*.json change, or undo the Figma edit).
  • Re-run the generators (step 2) and refresh (step 4) to confirm the value returns to baseline.

Expected figma:extract output — the warnings are normal

figma:extract fetches the whole file (GET /v1/files/:key) and locates data by walking the tree for frames/pages/sections with specific NAMES. Most of those names don't exist in this file, so it falls back gracefully. A typical run:

text

The run succeeds (graceful fallbacks, no crash) — the warnings are normal for how extract.ts is written. They reveal a real limitation: extraction is name/structure-dependent, and only buttons + checkbox + radio actually pull fresh values; the top-level light/dark palette (0 light + 0 dark) and icons / toggle / progress / slider / skeleton do not. Those values come from figma-corrections/.json + theme/defaults/.ts. This is precisely why only the button family is REST-verified and why the correction layer carries the rest.

The robust fix (the direction to take): fetch the NODES with all their info — target the real component nodes with GET /v1/files/:key/nodes?ids=… (full geometry + fills + boundVariables), exactly what the conformance generator already does for the buttons page. That makes extraction node-targeted and complete, independent of Figma's frame/page naming. (Tracked as the extract-rework — the map-the-master rule, see the conformance standard.)

How the Inspector property table is populated (dynamic values, curated schema)

The per-property table on the Button Inspector (columns Figma prop | Figma value | Figma variable | Light | Dark | CSS property | Token | CSS var | State) is rendered dynamically, not hand-authored. The data flow:

text extractCss()/buildVariant() --> button-variants.json --fetch--> VariationBlock.tsx (scripts/figma/lib/node-extract.mjs) (generate-button-conformance.mjs, (renders rows) public/conformance/)]]>
  • Rows are dynamic. VariationBlock.tsx maps over variation.properties[]; only the 9 column headers are a fixed array. index.tsx fetches /conformance/button-variants.json at runtime — so whatever the dataset contains is what renders.
  • Values are real/dynamic. extractCss() (scripts/figma/lib/node-extract.mjs) reads the actual node — fills, strokes, dimensions, padding, typography — and buildVariant() resolves per-mode Light/Dark via the figma-tokens.json variable join. No value is hand-typed.
  • The property SET is a curated fixed schema. extractCss() returns a fixed object of ~26 CSS-equivalent keys. A brand-new Figma property is not auto-discovered — capturing it means extending extractCss() (to read it) and adding it to MAP(group) in generate-button-conformance.mjs (to mark it mapped). Keys with no MAP entry render as unmapped (e.g. boxSizing, which is additionally a literal constant 'border-box' — layout/intrinsic).

Practical implication: to change a value, change Figma (or a correction) and re-run figma:sync — the table updates itself, no code edit. To surface a new kind of property, extend extractCss() + MAP once. Full zero-code auto-discovery of arbitrary node fields is a possible future enhancement, deliberately not the default (it would flood the table with Figma internals).
